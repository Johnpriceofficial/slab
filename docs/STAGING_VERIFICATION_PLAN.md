## 11. How zero unexplained skips are enforced

The `supabase-integration` job already fails when `numPendingTests + numTodoTests !== 0`
and when `numTotalTests === 0`. The suite uses a single top-level gate
(`const suite = LIVE ? describe : describe.skip`), so a missing credential turns into
**skips, never silent passes** — and skips fail the job. No `it.skip`, `it.todo` or
conditional early-return exists inside a live case.

## 12. How the temporary rollback trigger is installed

`installLinkFailureFixture(projectUrl, dbUrl, runId)`:

1. Refuses production-looking URLs.
2. Refuses a missing `SLABVAULT_TEST_DB_URL`.
3. Opens a `pg` client and creates
   `public.__test_force_link_failure()` plus a `BEFORE UPDATE ... FOR EACH ROW` trigger on
   `public.ai_analysis_runs`, raising `P0001` exactly when the target run's `slab_id`
   transitions from `null` to non-null — i.e. **after** `create_slab` has already run inside
   the same transaction.

Nothing about this fixture exists in migration 68; the migration has no testing hook.

## 13. How the trigger is restricted to one random test run

The raised exception is guarded by `new.id = '<runId>'::uuid`, where `runId` is a UUID
generated for that single case. Every other row updated during the run passes through
untouched, so the fixture cannot affect any other case or any other data.

## 14. How the trigger is removed in `finally`

The case wraps its body in `withCleanup(body, cleanup)`, whose `finally` calls
`removeLinkFailureFixture(sql)` — `drop trigger if exists …` then
`drop function if exists …` — and then closes the connection. Afterwards the test asserts
the trigger and function are **absent** by querying `pg_trigger` / `pg_proc`.

## 15. How cleanup failure fails the run

`withCleanup` awaits the cleanup inside `finally` and does not swallow errors, so a failed
drop or a failed teardown rejects and fails the test even when the body passed. The
teardown ledger case additionally asserts that every created user, run and slab was
recorded and removed; an unreconciled ledger fails the suite.

## 16. Every database record and temporary object created by the suite

- `auth.users` rows: owner, second owner (cross-account isolation), administrator,
  customer, profile-less, inactive and suspended identities.
- `public.profiles` rows for those users (including inactive/suspended states).
- `public.ai_analysis_runs` rows in `succeeded`, `needs_review`, `running`, `failed` states,
  including ownerless runs.
- `public.ai_field_evidence` rows, including deliberately foreign/mixed-owner evidence.
- `public.slabs` rows created by successful saves (with permanent inventory numbers/codes).
- Audit rows written by the wrapper.
- Consumed values from the inventory-number sequence (non-transactional — a rolled-back
  save permanently consumes one number; nothing depends on contiguity).
- Temporary objects: `public.__test_force_link_failure()` and its trigger on
  `public.ai_analysis_runs`.

## 17. How each is removed

Teardown runs in `afterAll` against a single authoritative ledger, in dependency order:
audit rows → evidence → slabs → analysis runs → profiles → `auth.admin.deleteUser(id)` for
every created identity. The fixture trigger and function are dropped in the owning case's
`finally` and their absence asserted. Any teardown error fails the run (§15).

## 23. Why that change is safe only after credentials and owner approval exist

Adding the line makes 89 currently-skipped cases execute. Those cases create and delete auth
users and install a temporary trigger on `ai_analysis_runs`. That is safe **only** against a
disposable stack whose non-production status has been proven (§7). Landing the line before

whatever database the job's environment happens to resolve to — and it would flip a required
check from "honestly skipped" to "executing destructive work" without a human decision.
Owner approval is the control that decides which database that is.
